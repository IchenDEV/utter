**Status:** approved
**Approved-by:** 用户（本对话：“不管怎么样，这就是比较好的交互，按照你约定的，直接全部开干。”）
**Approved-date:** 2026-10-06
**Risk:** high（麦克风、键盘完全访问、跨 App 跳转、向宿主字段写入文本、可能的云端文本发送）
**Upstream:** 用户（本对话，2026-10-06）：“现在交互还是不对。豆包输入法的交互是这样的，它点那个麦克风按钮，如果没有启动的话，自动跳转到主程序，然后再跳回来。这个时候自动激活麦克风，可以进行语音输入。并且语音输入是流式的，会在要输入的地方显示流式输出内容，而不是先要输出识别完了再点插入，这个交互很蠢。流式完了之后，大概还有一个对所有文字做整形的步骤，会调用一个语言模型，去对之前输入的文字做整形，类似于我们桌面端的操作。”
上游 bundle：`2026-10-04-ios-support`（含已批准的 `doubao-voice-parity.md`）、`2026-10-06-keyboard-native-alignment`（键盘外观，另见该 bundle 的追加条目）。

## Problem

今天的键盘听写要点三次、读一次结果：未待命时先点“打开 Utter 启用语音输入”链接，跳到主 App；自己切回；点语音键开始；点停止；等识别完成；结果出现在键盘上的卡片里；再点“插入”。用户要的是豆包式的一条线：点麦克风，其余自动完成，文字边说边出现在输入框里。

现状（代码核对，提交 `b351a8d` 之后的工作区）：

| 环节 | 现状 | 证据 |
| --- | --- | --- |
| 未待命时点麦克风 | 不是麦克风键，而是单独的链接键“打开 Utter 启用语音输入”，点后只跳转 | `KeyboardView.swift`，spec §3 `keyboard.activate` |
| 跳回宿主 | **没有**。主 App 不返回，用户自己切回 | iOS 无公开的“返回上一个 App”API；已批准 spec 与 `doubao-voice-parity.md` 明令不用私有 API/KVC |
| 跳转后自动开始录音 | 没有。键盘每次回到前台都撤销旧租约（`viewWillDisappear`），需用户再点一次 | `KeyboardController.swift`；`native-wake-research.md` “Integration constraints” |
| 流式 | 没有。桥状态的 `text` 只在 `result` 阶段有值，结果只能由 `consume` 一次性取走 | `BridgeMessages.swift`、`SharedVoiceBridge` |
| 识别中间结果 | Apple SpeechAnalyzer 路径只取 `result.isFinal`；旧引擎与会话事件 `transcriptPartial` 有中间结果但未接到键盘 | `AppleSpeechAnalyzer.swift:86,106`，`OpenTypeService.swift:132` |
| 结束后整形 | 移动端没有。桌面端的整理链在 macOS 模块里，iOS 只复用基础清理与词典 | `doubao-voice-parity.md`“文字整理”一行；仓库内没有 FoundationModels 用法 |
| 显式插入 | 是已批准的安全设计：原字段校验、单次消费、不自动插入 | 同上、spec 安全章节 |

## Outcome

在已通过待命门槛的前提下，键盘听写变成：

1. **一键进入**：待命已失效时，点麦克风键本身即跳到主 App 并完成待命（不再先点另一个链接键）。待命有效时，点击/按住直接开始。
2. **回到宿主后自动开始**：回到原来的输入框、键盘重新出现后，如果这是由刚才那次麦克风点击引起的跳转，则自动开始录音，不需要第二次点击。
3. **流式上屏**：识别过程中的文字直接出现在宿主输入框光标处，随识别修正原地替换，不累积重复；结束时输入框里的文字就是最终文字，不需要“插入”。
4. **结束后整形**：最终文字出来后，用语言模型对**本次听写的那一段文字**做标点、分段、口语清理和纠错，整段原地替换；失败或超时保留原文。
5. **可撤销、不越界**：一键撤销本次听写（删除整段，或还原为整形前的原文）；用户在听写期间移动光标、编辑、换字段、换 App 时立即停止写入，绝不删除不是我们写入的文字，绝不自动发送。

## 验收标准（可观察）

1. 待命失效时点麦克风键 **一次** 即打开 Utter 并进入 `active` 待命；不出现第二个需要点击的激活控件。
2. 返回宿主后（见决策 D1），键盘在 ≤ 1.5 秒内自动进入 `recording`，真机日志记录从键盘出现到录音首帧的时间；意图标记 ≤ 60 秒有效、只能使用一次；原字段变了（`documentIdentifier` 或上下文不符）则**不**自动开始，回到普通麦克风键。
3. 固定语音（沿用 `今天下午 3:00，我们在公园见面，请记得带一瓶水。`）播放期间，宿主输入框在语音开始后 ≤ 1.5 秒出现文字，并在播放结束前至少更新 2 次；结束后全文等于最终识别结果，且只出现一份（不重复、不残留中间稿）。
4. 三个宿主（设置搜索框、备忘录、Safari 网页文本域）各通过一轮；其中至少一个宿主的文本框带联想/自动更正。
5. 安全：流式过程中改光标位置、手动输入一个字、切到别的字段，三种情况下写入立即停止，宿主里只剩下已经写入的部分，且没有删除任何非我们写入的文字；不触发回车/发送。
6. 整形：最终文字之后 ≤ N 秒（N 在 spec 定，默认 4）整段替换为整形结果；整形期间用户动了光标或编辑则放弃替换；整形失败、超时、模型不可用时保留原文并有一行说明；整形结果不添加原文没有的信息（沿用 `voice_quality_fidelity` 校验）。
7. 撤销：一次点击把本次听写整段删除或还原为原文；撤销后宿主文本与听写前逐字符相同。
8. 隐私：中间稿与最终稿只经 App Group 桥传输，沿用租约/代次/过期语义；不落盘持久保存；整形若使用云端，必须是用户已配置并显式开启的提供方，默认关闭，且在键盘/设置里可见。
9. 现有门禁、真机键盘用例和 `check-ios-bridge.sh` 在不放宽断言的前提下通过；新增桥协议字段向后兼容或明确版本。

## Non-goals

- 不做拼音、手写、账号、跨端同步，不改变“闲时麦克风关闭”和“不用静音循环”。
- 不保证“无条件冷启动免跳转”：首次/待命失效时仍要经主 App 一次，这与已核对的豆包公开描述一致。
- 不对标豆包的内部实现，不反编译；未经证实的做法不当作事实。

## 必须由你决定的取舍

**D1 跳转后怎么回到原 App。** 这是本需求里唯一没有公开方案的一环。
- **A（我推荐）只用公开能力**：主 App 完成待命后显示明确的“返回”指引，用户用系统的返回入口（左上角“返回”面包屑，或手动切回）；回到键盘后按验收 2 自动开始录音。差距：多一次“切回”的操作，豆包是自动的。系统面包屑在 iPad 与不同入口下是否出现，需要真机核实，我现在不能保证。
- **B 使用私有 API 自动回到原 App**：能做到与豆包观感一致，但**违反已批准的 spec**（“不使用私有 API/KVC”）、`App Review` 对键盘启动其他 App 的限制，且我没有证据证明豆包是这样实现的。如果选 B，需要你明确批准并接受审核风险，我仍要先在真机上证明它在 iPadOS 27 可用。
- **C 先不做自动返回**，只做 1、3、4、5（一键进入、流式、整形、撤销）。

**D2 整形用哪个模型。**
- ① Apple 端侧模型（FoundationModels）：无需下载、数据不出设备；**我还没验证** iPad mini A17 Pro 上的可用性、中英混说质量和延迟，需要先做真机探针。
- ② 你已配置的远程 LLM：效果可控，但文字离开设备，需要显式开关；移动端目前没有这条链路。
- ③ 本地 MLX 模型：设备内下载仍有 TLS 失败，且体积/内存要评估，目前不可行。
- 我的建议：先探针 ①，可用就用 ①；不可用时 ② 且默认关闭。

**D3 取代“显式插入”。** 已批准的对标文档要求“显式插入”和“不自动插入”。你这次明确说它“很蠢”，所以我把它改成：流式写入加撤销，替代插入按钮；原字段校验保留，改为“写入过程中持续校验、失效即停”。请确认这就是你要的取代，而不是在两种模式间加一个设置开关。

## 风险与回滚

- 向宿主字段写入、删除是最大风险：宿主 App 对 `deleteBackward` + `insertText` 的反应不同（联想栏、实时搜索、受控输入框），所以验收 4、5 要求多个宿主与失效即停。
- 回滚：键盘端流式写入、自动开始和整形各自由独立开关控制，关闭后回到当前的“结果卡片 + 插入”；桥协议新增字段可选，旧键盘忽略。
- 高风险需要独立验证者复核，真机证据不能用合成桥替代。
