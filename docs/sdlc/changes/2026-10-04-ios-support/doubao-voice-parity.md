## 需要批准的具体设计变化

已批准 spec 规定：“Live Activity 不可用或后台启动失败 … 不创建隐藏 PiP”。保留的候选使用公开视频通话 PiP、单张本地固定帧和压缩内容尺寸，目前只存在于独立探针。建议允许它在通过下列组合门槛后，进入**用户明确启用、可随时关闭、可撤回的产品实现**。不放宽闲时不录音和外部视频共存要求。

1. 扩展已有独立探针，验证真实键盘命令、实际音频启动/停止及 Live Activity 创建；不能用合成文本或主 App 前台运行替代。
2. 验证五分钟闲置及外部视频两种顺序。分别记录 active/suspended/stopped、录音期间的音频帧、宿主前台状态和视频推进；脱离 XCTest 的对照运行后，才判断保活增益。
3. 全部通过后复用已有 controller/bridge 接入产品。首次激活由用户显式发起，停用入口始终可达；后台能力丢失时显示不可用，由用户重新激活，不恢复旧录音。
4. 不使用私有 API/KVC、静音循环、闲时持续麦克风、强制常亮或隐式云端回退。共存失败不能靠放宽断言通过。
5. 候选失败则保留证据并重新决策；每次跳转或常开麦克风不算对标完成。App Store 可接受性另行验证，本轮不发布。

用户另行明确批准上述后台设计变化及执行顺序，要求三项门槛不变。生产接入仍以真实结果为条件，未授权跳过验收或发布。

## 实施顺序与回滚

2026-10-06 用户“继续研发”授权继续独立验证。新增窄对照：不创建 PiP、无 AVAudioEngine/AudioUnit/Recorder、无输入 tap/播放，只以前台启动的 `playback + mixWithOthers` 或 `playAndRecord + mixWithOthers` 会话做待命假设；与完全无音频激活对照在脱离 XCTest/调试器的真机后台运行比较。记录 PID、journal 时间间隙、会话激活调用成功及现有 capture 状态；激活调用成功不代表系统仍保活或麦克风状态。先观察 85 秒，若没有保留能力就不进入真实语音/五分钟及视频验收。所有候选独立、不放宽三门槛；停止与恢复沿用原有回滚，不变更产品隐私或启用键盘语音。

2026-10-06 用户继续指令“继续解决PiP 共存问题”：在原已批准的独立探针及三项门槛内做因果隔离，先测只有 playback + mixWithOthers 音频激活而没有 Utter PiP，再测完全不操作探针音频会话的 video-call PiP，两种外部视频顺序均保留。这些短测试不请求真实录音、不播放语音、不把合成桥当真实输入验收；只有外部视频持续推进且后台能力仍可用，才继续真实语音及长期测试。新增 did-stop-before-cleanup journal 用于区分系统先停止与我们主动清理。公开头文件未提供多 PiP 并行开关；Apple 的 suspended 文档仅说明其他 PiP 使用时自身暂停/屏幕外，不承诺后台执行。不能通过自动重抢 PiP、删失败断言或放宽门槛来称为解决。

独立复核后追加普通 [sampleBufferDisplayLayer 内容源](https://developer.apple.com/documentation/avkit/avpictureinpicturecontroller/contentsource-swift.class/init(samplebufferdisplaylayer:playbackdelegate:)) 的窄对照，区分视频通话源与普通视频源的资源仲裁。复用固定帧，不录音、不使用静音循环；普通源不压缩窗口且不进入产品。其短时播放/状态通过也不满足无残留窗口、真实命令和长期待命门槛。相关 [suspended 定义](https://developer.apple.com/documentation/avkit/avpictureinpicturecontroller/ispictureinpicturesuspended) 不等同 stopped，更不提供后台执行承诺。

无 I/O 三组出现长执行空档后，再窄测公开 AVAudioRecorder 的前台 3 秒录音 → pause（保留会话）生命周期，区分从未启动 I/O 与已暂停的录音器。仅使用已授予的麦克风权限，不申请新权限；Mac 播放此前获授权的固定语音。诊断音频完全文件保护，暂停后才切后台，记录 isRecording/currentTime/计数；isRecording=false 不作为系统麦克风完整证明。无 PiP、无 ASR、无云端；录音器或后台执行未通过就不接入产品。停止及新进程 cleanup 仅删除专用 standby-paused-recorder.caf，恢复原 Release。

## 2026-10-06 外部产品实际行为核对（仅研究，未改代码/门槛/状态）

用户“继续解决pip 问题”。为判断“共存”应如何定义，核对了在售产品的公开实测记录；这些是用户观察，非官方实现说明，未反编译任何产品。

- Apple [isPictureInPictureSuspended 文档](https://developer.apple.com/documentation/avkit/avpictureinpicturecontroller/ispictureinpicturesuspended)：系统同一时间只给一个 App 的 PiP 会话；其他 App（典型为 FaceTime）使用时，本会话被挂起，不承诺后台执行。公开头文件无多 PiP 并行开关。
- [知乎实测（iOS 27 豆包 TestFlight）](https://www.zhihu.com/tardis/jm/art/2051352042984181943)：与系统听写、Siri 不冲突；“播放视频后最小化小窗，会和语音输入冲突，再次语音输入会重新弹出悬浮窗”，作者视为唯一不完美处；豆包与微信输入法同源，两者互相抢占。
- [V2EX 4 月讨论](https://www.v2ex.com/t/1205006)：另一 App 使用画中画时“会冲突，自动关闭前一个悬浮窗”。
- [V2EX 9 月复测](https://www.v2ex.com/t/1242988)：划掉后台后仍需跳转；说明依赖主进程长期在线。

据此，Utter 两种内容源、两种启动顺序的互相替换，与在售产品的已知行为一致，不是本探针的实现缺陷。官方“可与视频小窗共存”的措辞，实测记录只支持“不影响视频播放前提下可再次启动”（再次启动会重新占用 PiP），不支持“两个 PiP 同时存在”。“严格同时存在”未被任何公开证据证实。

待用户决定的修订（未批准前不改 spec/门槛）：

1. **A. 门槛 3 改为“可检测、可恢复的仲裁”**：外部 PiP 取代 Utter 时，键盘立即显示“待命已被其他小窗替换”，不假装可用；点一次经已验证的 `Link` 回主 App 重新待命（会重新占用 PiP，视频退回内嵌）。需真机验证检测延迟与恢复后原字段回填。
2. **B. 保持严格共存**：只能换保活机制。后台播放静音音频不创建 PiP 理论上能与视频共存，但已批准 spec 明确禁止静音循环；需用户单独批准后，先做独立真机探针（后台存活、闲时无麦克风橙点、与 Safari PiP 同时运行、App Store 可接受性）。位置定位保活不推荐：权限敏感且与用途不符。
3. **C. 暂停键盘免跳转**：保留主 App 内录音与“可见跳转”入口。
