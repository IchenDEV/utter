# Intent: 桌面端智能整理的数字规则与口述列表被守卫误退回

**Status:** approved
**Approved-by:** 用户（本对话：“批准并执行”，针对排查报告的 P0/P1 方案）
**Approved-date:** 2026-10-07
**Risk:** medium（改动文本处理的保真守卫、分类器和提示词；不改权限、数据与发布）
**Upstream:** 用户（本对话，2026-10-07）：“为什么这个指令效果不好？输出的阿拉伯数字都不是按阿拉伯数字输出的。第二个问题是专业模式下，像这种分标点的分数字分列表的没有被排列成一二三四。1. xxx”，以及“类似 typeless 的输出风格”。

## Problem

1. 编辑规则“所有数字都用阿拉伯数字”不生效：`Windows 七`、`cloud 五系列`、`gpt 六系列` 这类单字中文数字，模型输出阿拉伯数字后被 `TranscriptFidelityGuard` 判为 `protected_token_change`，整段退回原文。
2. 专业风格下口述的“第一个/首先/一、/问题一/一是”不排成 `1. 2. 3.`：分类器把“第一个”排除在序号之外；即使模型输出了编号，守卫也把新增的 `1. 2.` 当作新增数字而退回原文。
3. 自我纠正里的时间（“三点，不对，四点”）输出“4 点”同样被守卫否决。
4. 编辑规则在提示词里被当作数据；邮件/聊天契约没有语气规则；提示词缺少去口头禅、去重复示例。
5. 评测管线写死 `editRules: []`，无法回归编辑规则。

## Outcome

- 单字数字紧跟英文名称或型号时可以改写成阿拉伯数字，且不放开“统一”“一点意见”这类非数字词。
- 口述序号可以排成编号列表，且守卫仍拒绝丢导语、改数字、乱序编号。
- 自我纠正里的“数字+点/号/天/个”保留最终值。
- 编辑规则以用户明确指令的措辞进入提示词；邮件偏正式、聊天偏随意；提示词补充口头禅、重复、序号列表和单字数字示例。
- 评测语料可带 `edit_rules`，并新增对应用例。

## Scope

范围内：`UtterProcessing` 守卫/分类器/提示词、`UtterEvaluation` 语料字段、评测脚本、固定语料与文档。
非目标：不把编辑规则移进 system prompt（保持稳定前缀缓存，见 spec）；不增加按 App 名单的硬编码；不改历史页 UI；不做“守卫回退原因”的可视化（P2，另开 intent）。

## Constraints

- 项目原则：不硬编码口头禅删除，由 LLM 通过系统提示词处理。
- 守卫放宽必须对称、保守；现有保真测试全部保持通过。
- 每个文件 < 300 行；本地化提示词按语言分别维护。

## Acceptance criteria

1. `Windows 七 → Windows 7`、`cloud 五系列 → cloud 5 系列` 通过守卫；`统一处理 → 统 1 处理`、`一点意见 → 1 点意见`、`iPhone 一下子 → iPhone 1 下子` 仍被拒绝。
2. `第一个…第二个`、`首先/其次/最后`、`一、二、三、`、`问题一/二`、`一是/二是` 渲染为 `1. 2. 3.` 通过守卫；丢掉“三件事”导语、改动数字、编号不从 1 递增仍被拒绝。
3. 分类器把 `第一个…第二个`、`问题一…问题二`、`一、二、三、` 判为 `orderedSteps`；`我第一次来，第二天就走了`、`他是第一个到的` 仍为 `plainParagraph`。
4. `三点，不对，四点开会 → 4 点开会` 通过，`→ 5 点开会` 被拒绝。
5. 编辑规则段含“必须逐条遵守”；评测语料支持 `edit_rules` 并含 5 个新用例。
6. `bash scripts/ci-basic-checks.sh`、`bash scripts/sdlc-checks.sh`、`swift test` 通过。
