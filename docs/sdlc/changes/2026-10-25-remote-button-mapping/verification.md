### Observer under silence: pass for two keys

With Right (79) and OK (40) each mapped to nothing by `hidutil`, the non-seizing `IOHIDManager` saw all 3 presses and 3 releases of each, and the CG layer saw none (evidence `batch0-keytable-raw.txt`, lines 414 to 503; a stray volume-down hold and three Left presses by the user are in that window and are not from the mapped keys). The mapping read back as expected and was restored to F5 → nothing afterwards.
Not covered: silencing a **volume** key, whose native event is system-defined rather than a key event. It has the same usage page, so the same mechanism should apply, but it is untested.

### Timing (one user, ten deliberate quick double clicks)

- Short press hold: 0.135 to 0.36 s (median about 0.18 s). Holds during the double-click run: 0.075 to 0.255 s.
- Down-to-down gap of double clicks: 0.15 to 0.30 s (11 gaps; one run was a triple click). The slowest natural gaps were 0.285 and 0.30 s, so the 300 ms starting window has no margin; **proposed 400 ms**. The 500 ms long-press threshold sits above the slowest short press (0.36 s); **kept**.
- Both numbers come from one person pressing deliberately. They are starting values, not a user study.

### Input Monitoring (spec D2): partly measured

Measured from a minimal ad hoc signed `.app` launched with `open`, so it carries none of the host's permissions (the host process itself reports `IOHIDCheckAccess` = granted, so every earlier probe ran with Input Monitoring):

- `IOHIDManagerOpen` on the remote **fails with `0xe00002e2` (`kIOReturnNotPermitted`)** without the permission, although the device enumerates (1 matched). So M3's observer does need Input Monitoring.
- A first `IOHIDManagerOpen` call changes the state from unknown to **denied with no prompt**. The implementation must call `IOHIDRequestAccess` before opening, or the user is never asked.
- A first `IOHIDRequestAccess` call returned `false` at once, the state became denied at once, and a system dialog appeared (reported by the user).
- **User report: granting was inconvenient** (the dialog leads to a manual toggle in System Settings). The user did not complete the grant, so these were not measured: whether the same process receives events after a grant without relaunch, and whether a freshly launched process then opens without a prompt.
- An earlier run with no presses and a host-permission control (`batch0-perm-A2-*.txt`) is **not evidence** about events without permission: the control saw no presses either.

### Not run

- Crash heal after forced termination: PR #130's evidence already shows the mapping is lost when the remote disconnects and reconnects (new service appears without it), so silenced keys return at the next reconnect, or on a manual clear. Sleep and wake, and the idle disconnect time, are unmeasured.
- Under M1: private-usage viability (dropped from the plan's measurements when M3 was chosen).

### Cleanup state

Remote mapping read back as F5 → nothing (original). Volume restored to 69. Utter relaunched. Two ad hoc probe apps, `com.opentype.batch0probe` and `com.opentype.batch0probe.b`, may remain listed in System Settings → Privacy & Security → Input Monitoring as not enabled; they can be removed there.

## Batch 1: model and gesture recognizer (implemented 2026-10-25)

Files: `RemoteButton`, `ButtonAction`, `RemoteButtonProfile`, `ButtonGestureRecognizer`, `ButtonMappingPlan` in `Sources/UtterRemoteMic/` (all under 140 lines) and two test files, 45 tests. `swift test --filter UtterRemoteMicTests` runs 141 tests with no failure; `ci-basic-checks` passes.

Test strength was checked by mutation: changing `deadline <= time` to `<`, the release boundary `<` to `<=`, and the unknown-action default from `native` to `showDesktop` each make the suite fail (the second only after the boundary test was added, because the first draft of the tests missed it).

**Interpretation to confirm.** Erratum 1 says that with a double click bound and no long press, single fires "when W after the first press passes with no second press". The recognizer fires single at that moment only if the key was already released. A key still held when W ends is resolved at its release, so a key that is down never fires a single. The two readings agree for every press shorter than W (about 0.4 s); they differ only for holds between W and the long-press threshold on a button that has a double click bound and no long press. Changing it is one line plus one test.

## Batch 2: policy and controller generalization (implemented 2026-10-25)

Scope: the key remapping now owns a set of sources that can change while running, instead of the single F5 entry. Nothing in the app calls `setOwnedSources` yet, so behavior of PR #130 is unchanged until Batch 6 wires it.

- **Ownership is source based.** An entry is ours iff its destination is 0 and its source is F5 or one of the 11 remote button sources. A crash leftover written for a different profile is therefore recognized, repaired and cleaned on disable.
- **Editing is not a conflict.** When the desired set differs from the applied set the controller starts a fresh attempt (no re-apply counted, no conflict). Another tool overwriting an owned key still gets one re-apply and then a reported conflict, as in PR #130.
- **Restore is limited to what we silenced.** `applying` puts back an original entry only for a key we owned before and no longer want, and only when nothing else is on that source. This was found while writing tests: the first version also resurrected an unrelated original entry that another tool had removed meanwhile.
- **Read-back must match exactly.** A first version accepted any read-back that contained everything desired, which hid a released key left silenced after a failed write. `isSynced` now also rejects stale entries of ours.

Tests: 36 existing PR #130 mapping tests unchanged and passing; 14 new policy tests and 17 new controller tests; module total 172, 0 failures.
