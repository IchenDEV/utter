### Observer under silence: pass for two keys

With Right (79) and OK (40) each mapped to nothing by `hidutil`, the non-seizing `IOHIDManager` saw all 3 presses and 3 releases of each, and the CG layer saw none (evidence `batch0-keytable-raw.txt`, lines 414 to 503; a stray volume-down hold and three Left presses by the user are in that window and are not from the mapped keys). The mapping read back as expected and was restored to F5 → nothing afterwards.
Not covered: silencing a **volume** key, whose native event is system-defined rather than a key event. It has the same usage page, so the same mechanism should apply, but it is untested.

### Timing (one user, ten deliberate quick double clicks)

- Short press hold: 0.135 to 0.36 s (median about 0.18 s). Holds during the double-click run: 0.075 to 0.255 s.
- Down-to-down gap of double clicks: 0.15 to 0.30 s (11 gaps; one run was a triple click). The slowest natural gaps were 0.285 and 0.30 s, so the 300 ms starting window has no margin; **proposed 400 ms**. The 500 ms long-press threshold sits above the slowest short press (0.36 s); **kept**.
- Both numbers come from one person pressing deliberately. They are starting values, not a user study.

### Input Monitoring (spec D2): partly measured

Measured from a minimal ad hoc signed `.app` launched with `open`, so it carries none of the host's permissions (the host process itself reports `IOHIDCheckAccess` = granted, so every earlier probe ran with Input Monitoring):

- `IOHIDManagerOpen` on the remote **fails with `0xe00002e2` (`kIOReturnNotPermitted`)** without the permission, although the device enumerates (1 matched). So M3's observer does need Input Monitoring.
- A first `IOHIDManagerOpen` call changes the state from unknown to **denied with no prompt**. The implementation must call `IOHIDRequestAccess` before opening, or the user is never asked.
- A first `IOHIDRequestAccess` call returned `false` at once, the state became denied at once, and a system dialog appeared (reported by the user).
- **User report: granting was inconvenient** (the dialog leads to a manual toggle in System Settings). The user did not complete the grant, so these were not measured: whether the same process receives events after a grant without relaunch, and whether a freshly launched process then opens without a prompt.
- An earlier run with no presses and a host-permission control (`batch0-perm-A2-*.txt`) is **not evidence** about events without permission: the control saw no presses either.

### Not run

- Crash heal after forced termination: PR #130's evidence already shows the mapping is lost when the remote disconnects and reconnects (new service appears without it), so silenced keys return at the next reconnect, or on a manual clear. Sleep and wake, and the idle disconnect time, are unmeasured.
- Under M1: private-usage viability (dropped from the plan's measurements when M3 was chosen).

### Cleanup state

Remote mapping read back as F5 → nothing (original). Volume restored to 69. Utter relaunched. Two ad hoc probe apps, `com.opentype.batch0probe` and `com.opentype.batch0probe.b`, may remain listed in System Settings → Privacy & Security → Input Monitoring as not enabled; they can be removed there.

## Batch 1: model and gesture recognizer (implemented 2026-10-25)

Files: `RemoteButton`, `ButtonAction`, `RemoteButtonProfile`, `ButtonGestureRecognizer`, `ButtonMappingPlan` in `Sources/UtterRemoteMic/` (all under 140 lines) and two test files, 45 tests. `swift test --filter UtterRemoteMicTests` runs 141 tests with no failure; `ci-basic-checks` passes.

Test strength was checked by mutation: changing `deadline <= time` to `<`, the release boundary `<` to `<=`, and the unknown-action default from `native` to `showDesktop` each make the suite fail (the second only after the boundary test was added, because the first draft of the tests missed it).

**Interpretation to confirm.** Erratum 1 says that with a double click bound and no long press, single fires "when W after the first press passes with no second press". The recognizer fires single at that moment only if the key was already released. A key still held when W ends is resolved at its release, so a key that is down never fires a single. The two readings agree for every press shorter than W (about 0.4 s); they differ only for holds between W and the long-press threshold on a button that has a double click bound and no long press. Changing it is one line plus one test.

## Batch 2: policy and controller generalization (implemented 2026-10-25)

Scope: the key remapping now owns a set of sources that can change while running, instead of the single F5 entry. Nothing in the app calls `setOwnedSources` yet, so behavior of PR #130 is unchanged until Batch 6 wires it.

- **Ownership is source based.** An entry is ours iff its destination is 0 and its source is F5 or one of the 11 remote button sources. A crash leftover written for a different profile is therefore recognized, repaired and cleaned on disable.
- **Editing is not a conflict.** When the desired set differs from the applied set the controller starts a fresh attempt (no re-apply counted, no conflict). Another tool overwriting an owned key still gets one re-apply and then a reported conflict, as in PR #130.
- **Restore is limited to what we silenced.** `applying` puts back an original entry only for a key we owned before and no longer want, and only when nothing else is on that source. This was found while writing tests: the first version also resurrected an unrelated original entry that another tool had removed meanwhile.
- **Read-back must match exactly.** A first version accepted any read-back that contained everything desired, which hid a released key left silenced after a failed write. `isSynced` now also rejects stale entries of ours.

Tests: 36 existing PR #130 mapping tests unchanged and passing; 14 new policy tests and 17 new controller tests; module total 172, 0 failures.

Mutation checks (each applied alone, then reverted, sources diffed identical to the original):

| Mutation | Caught by |
|---|---|
| a profile edit is not recognized | 4 controller tests |
| read-back ignores stale entries | 3 tests |
| ownership ignores destination 0 | 5+ tests |
| disable ignores the carried state of a failed attempt | `testGivingUpAfterARetargetFailureStillRestoresOnDisable` |
| unknown sources accepted | 2 tests |

`bash scripts/ci-basic-checks.sh` and `bash scripts/sdlc-checks.sh` pass.

## Batch 4: press source and coordinator (implemented 2026-10-25)

Scope: `RemoteHIDPressSource` (non-seizing `IOHIDManager`), `RemoteButtonMappingCoordinator`, `RemoteButtonMappingState`. Nothing in the app creates them yet (Batch 6), so the shipped behavior is still PR #130's.

**The safety rule, as built.** A button is given to the key mapping controller only while the press source is `live` (Input Monitoring granted, manager open, a matching device present). Not live means an empty set, so only F5 stays silenced. Disabling hands the controller an empty set first and stops the observer second. Actions are emitted only while the key mapping reports `active`, so a key that is not yet silenced cannot fire its native event and the action together.

**Permission flow, as built (erratum 1).** `IOHIDCheckAccess` first; the system is asked (`IOHIDRequestAccess`) only when the user just turned the feature on or pressed the button on the page, and only if it has never been asked; the manager is opened only when access is granted, because a first open silently turns "not asked" into "denied". Granted yet refused (`kIOReturnNotPermitted`) is reported as `needsRestart`. The coordinator re-checks every second, when a device appears or disappears, and when the page asks.

**Decoding (from the Batch 0 raw log).** Each press arrives as a named element (usage = key, value 1 or 0) plus a rollover element (usage 1) and an array element (usage `0xFFFFFFFF`, value = the usage or a shifted copy). Only the named element with value 0 or 1 is an edge. A replay test feeds real raw values for one right and one OK press and expects exactly four edges.

Tests: 29 coordinator tests in 3 files (permission and source gating, losing and regaining the source, disable order, profile edits, gesture dispatch, decoding). Module total 187 tests, 0 failures.

Mutation checks (each alone, reverted, sources diffed identical): silence regardless of observation (9 tests fail), observer stopped before the silence is removed, no `active` gate on dispatch, pending gesture survives losing the source, recognizers rebuilt on every edit, always prompting, `evaluate` ignoring the enabled flag, state published on every call, decoder accepting any value. Each is caught.

**Real device, run by the implementer, no buttons pressed** (`evidence/batch4-press-source-smoke.txt`): with the host process holding Input Monitoring and the remote connected, `refresh` returned `live`, a second `refresh` was idempotent, one device-matched callback arrived, `stop` then `refresh` reopened, and a double `stop` did not crash.

**Not measured, and why it matters.**
- A grant given to a **fresh process**: whether `IOHIDCheckAccess` turns granted without a restart, and whether the open then works. The host here already had permission. If a restart is needed the page shows `needsRestart` only when the check says granted; if the check itself stays denied until restart, the page will keep saying "needs permission". The status text in Batch 7 will therefore say "if it still does not work after allowing, restart Utter". The independent verifier measures this on the signed build.
- Real presses through the new source while a mapping is active: Batch 0 measured raw edges under silence for right and OK only. The volume keys (media key path) were not measured under silence.
- Sleep, wake and idle disconnect.

`bash scripts/ci-basic-checks.sh` and `bash scripts/sdlc-checks.sh` pass.

## Batch 5: action executor (implemented 2026-10-25)

Scope: `ButtonActionPlanner` (pure), `ButtonActionExecutor`, `SystemInputPoster` (CGEvent, NSEvent, NSWorkspace). Not connected to the coordinator yet (Batch 6).

**What was measured here** (evidence `batch5-*.txt`; probe `batch5-ActionProbe.swift`):
- Show Desktop: synthetic F11 **with** the fn flag slid the probe window off screen and a second post restored it; F11 without fn did nothing. The system shortcut entry (hotkey 36) is not stored on this Mac, so the default is what ran. The executor reads the user's own entry when it exists (disabled turns the action off, a custom key is used).
- App switcher: Cmd+Tab as **flags on the Tab key alone did nothing**. Cmd down, Tab down and up, Cmd up as separate events switched to the previous app, with and without 40 ms gaps. So every chord is posted as modifier events plus key events.
- Media keys: volume down then up through the real poster read 69, 63, 69.
- Unknown bundle id: the poster returns false without side effects; the executor logs the kind only.

**Side effect of the measurement, disclosed.** In the first (broken) probe run the "undo" post of F11 went out while another app (Dia) was frontmost, because I had not yet guarded on the probe being frontmost. In a Chromium-based browser on macOS F11 does not toggle full screen, and Dia's window was afterwards an ordinary window of the usual size, so no visible effect was found. The probe now posts only while it is frontmost. While measuring, windows briefly slid away and the frontmost app changed.

**Behavior rules, as built.**
- While secure input is on every keyboard-shaped action is dropped with a log line: key chords, system keys, show desktop, app switcher and also the native replay of a silenced key. Opening an app is not keyboard input and still works. Consequence to confirm: an owned OK button cannot submit a password field while secure input is on.
- A failed post stops the action, but modifiers already pressed are still released, so none stays held system-wide.
- Logs contain the button, the trigger and the action kind. Not the key, not the bundle id.
- No shell, script or URL action exists in the type, the codec or the executor.

**Known limitations.**
- Synthetic modifier events pass through Utter's own hotkey tap like physical ones. A chord whose only modifier is the user's dictation modifier (Ctrl, Option or Shift) can look like a tap of the dictation hotkey. The fn flag on F11 is on a key-down, which that tap ignores. Not mitigated; a tag-and-ignore would change `HotkeyManager` and was out of scope.
- Show Desktop and the app switcher were measured only on this Mac's default shortcuts, one macOS version.

Tests: 26 (15 planner, 11 executor): exact event counts for every action and for native emulation of each button, chord order and cumulative flags, media key numbers, secure input per kind and per moment, unknown app, partial failure, log privacy, the Show Desktop preference parser on default, disabled, custom, unassigned and malformed entries. Module total 213 tests.

Mutation checks (each alone, reverted): secure input ignored, secure input also blocking open app, posting continues after failure, bundle id in the log, modifiers released in press order, app switcher with flags only, Show Desktop without fn, fn treated as a modifier key, disabled shortcut ignored, next and previous swapped, modifier release skipped on failure. Each is caught.
